# AI Future Radar — Autonomous Evolution Directive

## Mission

Continuously evolve the repository from a production news radar into an auditable Technology Intelligence and Foresight system, while preserving every existing production invariant. The terminal objective is `G9 — Final Production Acceptance`.

## Operating contract

Work autonomously and continuously. Do not wait for user confirmation between engineering gates. Never claim a gate passed without executable evidence from the repository, tests, CI, or production validation.

## Non-negotiable safety rules

1. Preserve fail-closed publication behavior.
2. Do not weaken, delete, bypass, or silence existing tests merely to obtain green CI.
3. Keep experimental evolution isolated from `main` until its acceptance gates pass.
4. Prefer deterministic, auditable logic for identity, provenance, scoring inputs, lineage, and state transitions.
5. LLMs may interpret evidence but must not silently become the source of truth for provenance or scientific validity.
6. Never equate source authority with evidence strength.
7. Never equate repetition with independent corroboration.
8. Never present speculation as established fact.
9. Preserve counter-evidence and uncertainty.
10. Every schema or policy change must have regression coverage.

## Council review model

Before accepting a material architectural change, evaluate it through these independent roles:

- Systems Architect — boundaries, coupling, resilience, data contracts.
- AI/ML Engineer — model use, evaluation, reproducibility, hallucination controls.
- Information Retrieval / Knowledge Graph Engineer — provenance, entity resolution, graph integrity.
- Science/Evidence Methodologist — evidence levels, independence, counter-evidence.
- Futures / Foresight Specialist — weak signals, drivers, uncertainty, scenarios.
- Emerging Technology Analyst — cross-domain convergence and technology trajectories.
- Reliability/DevOps Engineer — CI, observability, rollback, failure isolation.
- Product/Editorial Governance — relevance, novelty, signal-to-noise, publication safety.

A change that fails a critical reliability or provenance invariant must remain out of production regardless of feature value.

## Required architecture

`Discovery → Canonical Story → Signal Extraction → Persistent Trend Registry → Evidence Graph → Temporal Intelligence → Cross-Domain Convergence → Foresight Layer → Shadow Production → Controlled Production → Acceptance`

Keep publication as a separate concern from longitudinal intelligence.

## Gate sequence

### G0 — Architecture

Define contracts, boundaries, schemas, observability and rollback strategy.

### G1 — Deterministic Trend Engine

Detect reproducible clusters from signals with configurable thresholds.

### G2 — Persistent Registry

Maintain stable cluster identity and auditable merge/split/revival lineage.

### G3 — Evidence Intelligence

Represent claims, supporting evidence, counter-evidence, provenance and independent-source groups.

### G4 — Temporal Intelligence

Track trend states, acceleration, stagnation, fading, revival and disconfirmation over time.

### G5 — Cross-Domain Convergence

Detect evidence-backed convergence across independent domains. Treat convergence as a hypothesis, never automatic causality.

### G6 — Foresight Intelligence

Transform validated trends into drivers, uncertainties, impacts, risks, opportunities and scenario hooks. Explicitly label inference and speculation.

### G7 — Shadow Production

Run the intelligence layer against real historical/live inputs without affecting publication. Measure false clusters, missed signals, duplication, drift and stability.

### G8 — Controlled Production Integration

Expose only validated outputs to production behind safe gates, feature flags or equivalent isolation. Verify rollback and failure containment.

### G9 — Final Production Acceptance

Pass only when full tests, CI, regression, data-contract checks, provenance checks, shadow validation and production invariants are green on the accepted revision.

## Autonomous execution loop

For every gate:

1. Inspect current repository state and existing contracts.
2. Identify the smallest architecture-consistent change.
3. Implement it on the evolution branch.
4. Add or update tests before declaring completion.
5. Run repository quality checks and inspect failures.
6. Fix root causes, not symptoms.
7. Re-run until deterministic failures are eliminated.
8. Review the diff for regressions, unnecessary complexity and security issues.
9. Record acceptance evidence.
10. Only then advance to the next gate.

If CI infrastructure is unavailable, record `VALIDATION BLOCKED`; do not manufacture a pass. If a write capability is unavailable, preserve the plan and report the exact blocker rather than claiming completion.

## Quality criteria for Trend Clusters

A cluster should become a high-confidence trend only when supported by sufficiently independent evidence over time. Volume alone is not enough. The system should reward novelty, independent corroboration, temporal persistence and cross-domain convergence, while penalizing repost cascades, source concentration, contradiction and transient media spikes.

## Completion definition

The project is complete only when `G9` is demonstrably satisfied. At that point the repository must contain:

- production-safe Trend Intelligence;
- persistent trend and evidence lineage;
- temporal state tracking;
- cross-domain/meta-trend detection;
- calibrated foresight outputs with uncertainty;
- regression and integration tests;
- CI evidence;
- shadow-production validation evidence;
- rollback/failure-containment behavior;
- updated architecture and operator documentation.

Until then, use `IMPLEMENTED`, `VALIDATION PENDING`, `BLOCKED`, or `PASS` precisely; never use `COMPLETE` prematurely.
